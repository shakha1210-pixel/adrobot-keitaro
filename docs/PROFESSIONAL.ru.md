# Профессиональное техническое руководство

Документ для разработчиков, code reviewers и инженеров, сопровождающих Adrobot.

## 1. Технический профиль

- Python 3.11+, FastAPI, Pydantic Settings.
- Асинхронный HTTP-клиент для Keitaro Admin API v1.
- SQLAlchemy 2.x и Alembic; SQLite по умолчанию, PostgreSQL через `DATABASE_URL`.
- Vanilla JavaScript UI, отдаваемый FastAPI как static files.
- pytest + respx, Ruff, GitHub Actions.

## 2. Границы ответственности

Keitaro остаётся источником истины для кампаний, потоков и офферов. Локальная БД Adrobot хранит журнал операций (`operation_log`), а не копию бизнес-сущностей. В приложении нет пользовательской аутентификации и разграничения ролей; текущая модель рассчитана на локальное/контролируемое использование.

## 3. Архитектурные слои

- **Routers** — HTTP-контракт и маршруты: meta/health, offers, campaigns, operations.
- **Services** — сценарии создания/редактирования кампаний, поиск офферов, разрешение справочников, отчётность и аудит.
- **Keitaro client** — транспортный слой: таймауты, классификация ошибок, безопасная политика повторов.
- **DTO / schemas** — нормализация ответов внешнего API и валидация входящих запросов.
- **Persistence** — SQLAlchemy-модель журнала операций и Alembic migrations.
- **Static UI** — интерфейс на русском и узбекском языках.

Подробные схемы и последовательности: [ARCHITECTURE.ru.md](ARCHITECTURE.ru.md).

## 4. Сценарий создания кампании

1. Валидировать имя, ISO-гео и offer ID.
2. Проверить существование выбранного offer.
3. Разрешить имена домена, группы и источника в Keitaro IDs.
4. Создать кампанию.
5. Создать GEO stream с country filter и redirect action.
6. Создать catch-all stream с выбранным offer.
7. Прочитать кампанию/потоки обратно и проверить фактическую конфигурацию.
8. Зафиксировать результат в operation log.

При частичном сбое известная кампания архивируется через компенсирующую операцию. Если POST завершился неоднозначно и ID кампании неизвестен, сервис не делает слепой повтор: оператор должен проверить состояние в Keitaro.

## 5. Сценарий редактирования

Редактор изменяет привязки офферов, сохраняя исходное представление потока и его неуправляемые поля. Доли пересчитываются так, чтобы сумма составляла 100%; удаление последнего offer запрещено. Для реального Keitaro офферный поток использует `schema: "landings"`; совместимость со старым представлением `offers` обрабатывается на уровне адаптации.

## 6. Политика повторов и ошибок

- GET и другие безопасные/idempotent операции могут повторяться при сетевых сбоях, 5xx и 429.
- Создающие POST-запросы не повторяются автоматически: внешний API не предоставляет idempotency key, а timeout не доказывает, что операция не состоялась.
- Внутренние детали внешней ошибки не должны утекать в публичный HTTP-ответ.
- Отчётная статистика может деградировать отдельно от основного сценария редактора.

См. также раздел «Надёжность интеграции с Keitaro» в [основном README](../README.md).

## 7. Конфигурация и миграции

Все параметры загружаются из `.env` / environment variables через Pydantic Settings. Шаблон — [../.env.example](../.env.example).

```bash
alembic upgrade head
alembic current
alembic downgrade -1
```

SQLite используется по умолчанию. Для PostgreSQL задайте корректный SQLAlchemy URL в `DATABASE_URL` и убедитесь, что драйвер установлен в окружении.

## 8. HTTP-контракт

| Метод | Endpoint | Назначение |
|---|---|---|
| GET | `/health`, `/health/live`, `/health/ready` | здоровье и готовность |
| GET | `/api/meta` | параметры UI и состояние конфигурации |
| GET | `/api/offers?q=` | поиск офферов |
| POST | `/api/campaigns` | создание кампании |
| GET | `/api/campaigns?prefix=1&q=` | список кампаний |
| GET | `/api/campaigns/{id}` | кампания, потоки, офферы, статистика |
| POST | `/api/campaigns/{id}/streams/{sid}/offers` | добавить offer |
| DELETE | `/api/campaigns/{id}/streams/{sid}/offers/{oid}` | удалить offer |
| GET | `/api/operations?limit=50` | журнал операций |

Каждый ответ содержит `X-Request-ID`. Формат ошибок: объект `error` с кодом и безопасным сообщением. Основные коды: validation, not_found, conflict, keitaro_unavailable, keitaro_error, keitaro_ambiguous, internal.

## 9. Качество и тестирование

Текущий набор содержит 58 тестовых функций. Проверки:

```bash
ruff check .
ruff format --check .
pytest -v
node --check static/app.js
alembic upgrade head
```

Windows shortcut: `.\scripts\check.ps1`. Тесты интеграции с Keitaro используют respx и не должны обращаться к реальному трекеру. CI workflow проверяет линт, тесты на Python 3.11–3.13, миграции на чистой БД и синтаксис frontend.

## 10. Безопасность и эксплуатационные ограничения

- Не коммитьте `.env` и не включайте API key в логи или issue.
- Сервис не имеет встроенной аутентификации; не выставляйте его напрямую в публичный интернет.
- Для внешнего развёртывания добавьте authentication/authorization, TLS reverse proxy, секрет-хранилище, ограничение сетевого доступа и мониторинг.
- Приложение пишет логи в stdout/stderr; ротация и долговременное хранение должны обеспечиваться средой запуска.
- Журнал операций не идентифицирует пользователя, поскольку пользовательская auth-модель отсутствует.
